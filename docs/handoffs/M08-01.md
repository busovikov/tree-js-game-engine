# Handoff: M08 browser project TypeScript/build/trust tooling

## Objective

Continue M08 from a clean, verified browser-tooling checkpoint. The completed slices define
trust and capability gates before compilation, a conflict-safe local workspace, deterministic
shared TypeScript project files, lazy TypeScript/bundler workers, separate gameplay/editor
bundles, and replaceable lazy Monaco/external VS Code adapters. Disposable Play transport and
the user-facing browser code workflow remain intentionally unstarted.

## Decisions and invariants

- `@haku/build` is created in M08 as assigned by the architecture. It has no editor or React
  dependency and is not a dependency of production games.
- Trust and per-project capability approval run before the injected worker boundary. An
  untrusted or unapproved request cannot instantiate TypeScript, Monaco, or esbuild.
- `BrowserProjectWorkspace` compares disk text, size, and `lastModified`, rechecks before
  save, and preserves dirty editor text on conflict. Only explicit `reload-disk` or
  `keep-editor` resolves a conflict.
- Built-in workspace mutation throws. Forking copies deterministic sorted file paths and
  opens the destination as `local-trusted`.
- Generated tooling has one frozen `files` object exposed as `monacoFiles` and `vsCodeFiles`;
  do not generate editor-specific declaration variants.
- Worker RPC clients create no Worker at module evaluation, reuse one worker after the first
  request, reject pending work on crash/dispose, and terminate explicitly.
- esbuild-wasm runs inside the bundler Worker with `worker: false`, because it is already off
  the main thread. Its virtual filesystem reads only the request file map.
- Monaco 0.56 uses its ESM package exports and explicit editor/TypeScript workers. The
  adapter is reachable only through the dynamic default provider import.
- Monaco's bundled TypeScript enum exposes `ESNext`/`NodeJs`, not
  `ES2022`/`Bundler`; generated VS Code/standalone TypeScript tooling retains the documented
  `ES2022`/`Bundler` tsconfig. Both consume the exact same declarations.
- Official patterns used:
  - https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API
  - https://vite.dev/guide/features.html#web-workers
  - https://esbuild.github.io/api/#running-in-the-browser
  - https://github.com/microsoft/monaco-editor
  - https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/getFile
  - https://developer.mozilla.org/en-US/docs/Web/API/FileSystemHandle/queryPermission
  - https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers
  - https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe
  - https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage

## Risks and open defects

- `BrowserProjectWorkspace` is verified but not yet instantiated by `ProjectService`; current
  scene/graph file paths still use their pre-M08 storage behavior.
- The bundler keeps `@haku/*` imports external. Disposable Play must provide an explicit,
  capability-limited runtime import strategy before a bundle using those imports can run.
- Monaco 0.56's root ESM export includes many languages and produces a large lazy chunk.
  It is correctly absent from the entry and game bundle, but can be narrowed later without
  weakening the provider boundary.
- The external VS Code helper needs an absolute path entered by the user because browser
  directory handles intentionally do not expose native absolute paths.
- No user-visible flow exists yet, so M08 acceptance is not complete.
