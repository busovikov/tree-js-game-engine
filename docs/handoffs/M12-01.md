# Handoff: M12 deterministic route generator and reachability solver

## Objective

Complete the first bounded M12 semantic slice: a pure, horizon-stable seeded route generator
with a fixed-step reachability solver, guaranteed center-to-center main route, explicit safety
margins, bounded deterministic fallback, complete decision evidence, mass-seed validation, and
one headless Rapier boundary comparison. Runtime pooling, replay, observations, and browser QA
remain later M12 slices.

## Scope and acceptance criteria

- [x] Same immutable seed/config returns the identical complete platform sequence and decision
      log.
- [x] Shorter generated routes are exact prefixes of longer routes with the same seed/config,
      so a future infinite track can extend without rewriting prior decisions.
- [x] The solver shares the current 60 Hz controller values for forward/lateral motion, bounce,
      gravity, ball radius, edge safety, and collision-event timing.
- [x] The start platform is safe and every mandatory transition retains explicit non-zero
      forward, lateral, and vertical margins as difficulty ramps.
- [x] Every generated sequence contains a center-to-center reachable main route; optional risky
      alternatives are not required and were not added.
- [x] Candidate attempts are bounded at 0–32, default to 6, and a zero-attempt deterministic
      fallback remains reachable.
- [x] Invalid config, vertical/forward/lateral boundaries, fallback, platform intersections,
      invalid surface gaps, continuity, and attempt overflow have focused coverage.
- [x] 256 seeds × 128 platforms validate without intersections, invalid gaps, missing routes,
      or attempt overflow.
- [x] One same-height trajectory boundary agrees exactly with headless Rapier collision tick and
      forward position.
- [x] No runtime integration, infinite pooling, replay/observation API, Playwright/Chrome work,
      M13, or M14 work entered this slice.

## Decisions and invariants

- Complex route mathematics remains typed project TypeScript. No Bounce Run-specific graph node
  or engine service was introduced.
- `BOUNCE_RUN_PHYSICS` is the single value source for both `BounceRunControlSystem` and the route
  solver. Runtime behavior is unchanged by the constant extraction.
- The solver uses the analytic descending ballistic root, quantizes it to 60 Hz, and adds the
  one collision-event latency tick proven by Rapier. Lateral travel uses the controller's exact
  fixed-tick exponential response.
- A platform landing is inset by ball radius plus `0.15` edge safety. Required generation safety
  decreases from `0.9` to `0.35` over a fixed 64-platform ramp and never depends on the requested
  horizon.
- Mandatory forward positions are centered on the predicted landing. This makes every selected
  landing the launch center for the next transition rather than merely putting the ball somewhere
  inside the prior target.
- Generated main platforms are pure descriptors (`4 × 0.6 × 4.2`, safe start
  `6 × 0.6 × 8`). Runtime code does not yet instantiate or size these descriptors.
- The decision log has one entry per platform, including every rejected candidate position,
  rejection reason, selected reachability result, attempt bound, difficulty, and required margin.
- Seeds are finite integers. Counts are bounded to 2–10,000. Candidate bounds are integers 0–32.
- Route validation is intentionally pure and checks all platform pairs. It is test/QA evidence,
  not a per-fixed-tick runtime operation.

- The running game still uses the M11 finite six-platform positions. No generated descriptor is
  instantiated at runtime yet.
- Generated sizes differ from the current fixed prefab geometry/collider dimensions. The pool
  integration must use public serializable component/transform updates and reconcile render and
  physics together; it must not treat a visual-only scale as proof of collider size.
- Lateral reachability proves existence from zero lateral velocity to the target center under the
  controller envelope. It does not emit a player input script and is not a QA bot.
- The Rapier comparison covers one same-height centered boundary. Vertical/lateral candidate
  matrices remain useful later integration coverage, but the current mass suite is pure.
- Route validation is quadratic for complete pair intersection evidence at the allowed maximum
  count. Generation attempts are bounded, and the tested 128-platform mass horizon is fast; do
  not run the complete validator every gameplay tick.
- Rapier emits its known initialization compatibility deprecation warning.
