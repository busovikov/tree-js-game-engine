## Decisions and invariants

- Actual browser QA used only the user's Chrome extension browser-client and in-skill
  `tab.playwright`. No bundled Chromium, new profile, in-app browser, standalone Playwright runner,
  or unrun standalone spec was used or added.
- Official Playwright keyboard documentation defines `keyboard.down()` and `keyboard.up()` as the
  separate hold/release primitives, while `press()` is the down/up shortcut:
  https://playwright.dev/docs/api/class-keyboard
- Official viewport, console, and failed-request contracts are:
  https://playwright.dev/docs/api/class-page#page-set-viewport-size,
  https://playwright.dev/docs/api/class-page#page-event-console, and
  https://playwright.dev/docs/api/class-page#page-event-request-failed.
- The installed browser-client documentation and live surface expose `locator.press` but no
  `tab.playwright.keyboard`, page-level press, separate down/up, or network-event API. The report
  records these as blockers instead of substituting another browser surface.
- `pressedThisFrame` is a generic action-map sampling latch. A non-repeated bound keydown is visible
  through the next `snapshot()` even if keyup arrives first; `endFrame()` clears the latch, while a
  still-held key remains in the normal pressed set.
- The DEV-only hold-right action remains a public gameplay action port. It proves sustained
  multi-tick control but is explicitly not physical-keyboard evidence.
- Production remains free of observation/report/action hooks. The existing production-boundary
  regression was retained and passed without weakening.
- The committed browser workflow report requires canonical step order, exactly development then
  production runs, exact DEV/production QA-hook expectations, bounded text/diagnostics, official
  Playwright sources, and only the exact Rapier warning whitelist.
